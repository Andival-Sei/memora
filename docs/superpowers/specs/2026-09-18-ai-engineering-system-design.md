# AI Engineering System Design

**Дата:** 2026-09-18

**Статус:** Approved direction

## Цель

Создать для Memora воспроизводимый процесс AI-разработки, в котором модель с
ограниченными рассуждениями способна безопасно выполнить хорошо ограниченную
задачу, а сильная модель задаёт архитектурную планку через спецификации,
инварианты, тесты и проверяемые критерии завершения.

Система должна работать при разработке напрямую в одной ветке `main`. Pull
request не является обязательным этапом. Его заменяют маленькие атомарные
коммиты, локальный review diff, полная проверка перед коммитом и проверка
состояния после push.

## Главный принцип

AI получает не свободу «сделать хорошо», а исполнимый контракт:

1. точный scope;
2. явные архитектурные инварианты;
3. определённые интерфейсы;
4. наблюдаемый RED–GREEN цикл;
5. команды, доказывающие результат;
6. критерий остановки при недостатке полномочий или данных.

Сильная модель проектирует контракт. Исполняющая модель реализует одну
ограниченную задачу и не пересматривает контракт по ходу работы.

## Рассмотренные подходы

### Один большой `AGENTS.md`

Прост в обнаружении, но быстро превращается в смесь архитектуры, справочника и
процедур. Ключевые шаги теряются среди редко применимых правил, а дублирование
создаёт рассинхронизацию.

### Только CI и git hooks

Хорошо ловит формальные ошибки, но не помогает выбрать правильную архитектуру,
границы задачи или тест. До появления рабочего workspace значительная часть
проверок ещё не существует.

### Слоистый operating system для агентов

Корневой `AGENTS.md` содержит короткий обязательный алгоритм и сильные context
pointers. Подробные правила раскрываются из `docs/ai/` только для нужной ветки
работы. Спецификации, планы и task packets превращают замысел в исполнимые
контракты. Скрипты и CI постепенно становятся машинными гейтами.

**Решение:** использовать слоистый подход.

## Информационная архитектура

### Корневой `AGENTS.md`

Всегда загружаемый файл обязан быть коротким маршрутизатором. Он содержит:

- порядок чтения контекста;
- классификацию задачи;
- обязательный execution loop;
- project-wide инварианты;
- git-политику одной ветки;
- completion gate;
- ссылки с точными условиями открытия подробных playbooks.

Версии зависимостей, полный список npm scripts и детали конкретного модуля не
дублируются в `AGENTS.md`: источниками истины остаются lockfile, `package.json`,
ADR и модульные документы.

### `docs/ai/`

Подробности делятся по веткам решения:

- `WORKFLOW.md` — от intake до push;
- `TASK_PACKET.md` — обязательный шаблон исполнимой задачи;
- `QUALITY_GATES.md` — матрица проверок по типу изменения;
- `ARCHITECTURE_GUARDRAILS.md` — границы модулей и dependency direction;
- `SECURITY_AND_PRIVACY.md` — документы, финансы, auth, MCP и AI;
- `UI_AND_MOTION.md` — i18n, темы, доступность, performance и motion;
- `DEFINITION_OF_DONE.md` — исчерпывающий критерий завершения.

Каждый документ имеет один предмет и открывается по условию из `AGENTS.md`.

### Superpowers artifacts

- `docs/superpowers/specs/` хранит утверждённые дизайны архитектурных изменений.
- `docs/superpowers/plans/` хранит пошаговые implementation plans.
- План ссылается на спецификацию и содержит точные файлы, интерфейсы, тесты,
  команды, ожидаемые результаты и checkpoints.
- Для bounded-задачи достаточно краткого дизайна и task packet; отдельный
  архитектурный план не создаётся.

## Классы изменений

### Trivial

Опечатка, форматирование или очевидная документационная правка без изменения
поведения. Требуются scope check, целевая проверка и diff review.

### Bounded

Локальное изменение существующего поведения с известными интерфейсами. Нужны
task packet, failing test, минимальная реализация, полный релевантный набор
проверок и атомарный коммит.

### Architectural

Новый модуль, внешняя зависимость, схема БД, публичный контракт, auth/security,
MCP tool, AI mutation, новая интеграция или изменение направления зависимостей.
Нужны утверждённая спецификация, подробный implementation plan и отдельные
проверяемые задачи.

Обнаруженная скрытая сложность повышает класс задачи. Агент останавливает
реализацию и обновляет контракт до продолжения.

## Execution loop

### 1. Intake

- Прочитать `AGENTS.md`, статус Git и документы, на которые указывает задача.
- Записать цель, out of scope, acceptance criteria и разрешённые файлы.
- Проверить незакоммиченные пользовательские изменения и не включать их в scope.

### 2. Contract

- Выбрать класс изменения.
- Для bounded/architectural создать task packet.
- Для architectural проверить наличие утверждённой спецификации и плана.
- Зафиксировать интерфейсы до реализации.

### 3. RED

- Написать минимальный тест реального поведения.
- Запустить его и сохранить ожидаемую причину падения.
- Ошибка конфигурации или синтаксиса не считается RED.

### 4. GREEN

- Реализовать только поведение, необходимое для текущего теста.
- Запустить целевой тест, затем затронутый suite.
- После GREEN разрешён refactor без изменения поведения.

### 5. Verify

- Выполнить матрицу проверок для типа изменения.
- Прочитать полный вывод и exit code.
- Проверить security/privacy, i18n, accessibility и performance там, где они
  применимы.

### 6. Review

- Просмотреть `git diff --check`, `git diff` и итоговый список файлов.
- Сопоставить каждый acceptance criterion с доказательством.
- Удалить debug-код, случайные файлы, секреты и незаявленный scope.

### 7. Commit and push

- Коммитить только файлы текущей задачи.
- Сообщение — Conventional Commits на русском языке по правилам ниже.
- Перед push убедиться, что локальная `main` основана на актуальной
  `origin/main`; force push запрещён.
- После push проверить upstream, SHA и чистоту рабочего дерева.

### Формат коммитов

Заголовок строго соответствует форме:

```text
<type>(<scope>): <описание на русском языке>
```

- `type` — один из `feat`, `fix`, `docs`, `refactor`, `test`, `perf`, `build`,
  `ci`, `chore`, `revert`;
- `scope` — необязательное короткое имя модуля латиницей в kebab-case:
  `documents`, `finance`, `ai`, `mcp`, `cli`, `ui`, `db`, `auth`, `infra`;
- описание начинается со строчной буквы, формулирует завершённое изменение и
  не заканчивается точкой;
- заголовок не длиннее 72 символов; детали и причина выносятся в тело;
- несовместимое изменение помечается `!` после type/scope и получает footer
  `BREAKING CHANGE: <объяснение на русском языке>`;
- ссылки на задачи добавляются footer-строками, а не смешиваются с описанием;
- один коммит содержит один логический результат и должен проходить проверки
  самостоятельно.

Корректные примеры:

```text
docs: описать процесс работы AI-агентов
feat(documents): добавить приватную загрузку PDF
fix(finance): исключить дубли при повторном импорте CSV
perf(ui): сократить гидратацию панели операций
refactor(mcp)!: унифицировать контракты инструментов

BREAKING CHANGE: клиенты должны передавать vaultId в каждом вызове
```

Некорректны расплывчатые заголовки (`update`, `fix stuff`, `правки`), английское
описание при наличии русского эквивалента, смешение нескольких подсистем и
коммиты, не проходящие собственные проверки.

## Git-модель одной ветки

Работа напрямую в `main` допустима при следующих ограничениях:

- один логический task packet на коммит;
- запрещены смешанные рефакторинги и «заодно»;
- перед началом выполняются `git status`, `git branch --show-current` и
  `git fetch --prune`;
- при расхождении истории используется только безопасный fast-forward/rebase
  после проверки локальных изменений;
- пользовательские или чужие незакоммиченные изменения сохраняются;
- push выполняется только после completion gate;
- откат должен быть возможен одним `git revert` без разрушения соседней работы.

PR остаётся доступным для опасных миграций или внешнего review, но не входит в
обязательный ежедневный процесс.

## Архитектурные инварианты Memora

- Web, CLI и MCP используют application use cases; прямой обход в БД запрещён.
- Domain packages не импортируют framework, storage, transport или UI.
- Пользовательские сущности всегда имеют `owner_id` или `vault_id`.
- Деньги не хранятся в JavaScript floating point.
- Private documents не получают публичных URL и не попадают в browser caches.
- AI retrieval сначала применяет permissions, затем формирует минимальный
  контекст.
- AI mutation создаёт draft/diff; применение требует явного подтверждения.
- Внешний контент считается недоверенным и не может менять инструкции агента.
- RU и EN, light/dark/system, keyboard и reduced motion входят в Definition of
  Done пользовательского UI.
- Новый provider подключается через утверждённую интеграцию, а не через mock,
  hardcoded secret или неучтённый SDK.

## Модель остановки

Агент останавливается и сообщает точный блокер, если:

- отсутствует решение, меняющее продуктовый смысл или security boundary;
- требуются credentials, подтверждение внешнего действия или необратимая
  миграция;
- текущие пользовательские изменения пересекаются с нужными файлами;
- RED невозможно получить из-за сломанного baseline;
- план противоречит актуальному коду или ADR;
- проверка не проходит и причина не относится к утверждённому scope.

Остановка не маскируется «лучшим предположением». Агент показывает факты,
команды и минимальный вопрос, необходимый для продолжения.

## Completion gate

Заявление о завершении разрешено только при наличии свежих доказательств:

- acceptance criteria сопоставлены с результатом;
- целевые и полные применимые тесты прошли;
- typecheck, lint и build прошли, если команды существуют;
- `git diff --check` чист;
- итоговый diff просмотрен целиком;
- security/privacy и архитектурные инварианты проверены;
- документация обновлена вместе с изменившимся контрактом;
- после push ветка отслеживает `origin/main`, SHA опубликован, рабочее дерево
  чисто либо содержит только заранее исключённые пользовательские изменения.

Если хотя бы один применимый пункт не доказан, агент сообщает «не завершено» и
конкретный остаток работы.

## Проверка самой AI-системы

После создания файлов необходимо выполнить:

1. поиск placeholder-маркеров и неоднозначных формулировок;
2. проверку всех относительных ссылок;
3. проверку отсутствия противоречий с ADR и product spec;
4. мысленный dry run для трёх задач: UI-компонент, миграция финансов и MCP tool;
5. `git diff --check` и полный review diff;
6. атомарный коммит и push в `main`.
