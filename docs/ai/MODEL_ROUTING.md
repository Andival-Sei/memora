# Маршрутизация моделей

Цель маршрутизации — дать дешёвой модели только ту работу, где результат
ограничен контрактом и автоматически проверяется. Название модели не заменяет
проверки: любой исполнитель обязан соблюдать `AGENTS.md`.

## Уровни работы

### Tier A — Sol/Astra

Используй сильную модель для хотя бы одного из условий:

- новая архитектура, модуль или направление зависимостей;
- schema migration, money representation или data retention;
- auth, permissions, encryption, secrets или private documents;
- новый внешний provider/dependency или production configuration;
- новый MCP resource/tool, AI mutation, agent loop или prompt-injection boundary;
- публичный API/contract, breaking change или cross-module refactor;
- неоднозначный дефект, flaky test, performance/security incident;
- нет тестового baseline либо acceptance criteria допускают два толкования.

Tier A пишет/утверждает спецификацию и план, определяет интерфейсы, threat model,
проверки и task packets. Реализация отдельных leaf tasks может быть передана
ниже только после прохождения Luna gate.

### Tier B — Terra или Sol с пониженным reasoning

Подходит для bounded-задач средней сложности: один известный модуль, ясные
интерфейсы, существующие тесты, несколько связанных файлов. Tier B может
исправлять обычные дефекты, добавлять локальные use cases и выполнять task из
утверждённого архитектурного плана. Изменение инварианта возвращает задачу Tier A.

### Tier C — Luna

Luna выполняет только leaf task: механическую, локальную и полностью
проверяемую работу. Примеры после появления baseline:

- добавить RU/EN copy одновременно в существующую схему сообщений;
- реализовать компонент по готовому API и тестам;
- добавить unit test для уже определённого поведения;
- выполнить локальный рефакторинг без изменения public contract;
- обновить документацию по уже принятому решению;
- исправить конкретный lint/type error без изменения архитектуры.

## Luna gate

Перед переключением на Luna все ответы должны быть **да**:

- [ ] Задача classified как bounded leaf task.
- [ ] Существует утверждённый task packet без двусмысленных полей.
- [ ] Указаны точные allowed files и out of scope.
- [ ] Интерфейсы и acceptance criteria уже выбраны Tier A/B.
- [ ] Baseline tests/typecheck/lint/build, применимые к scope, зелёные.
- [ ] Известна команда RED и ожидаемая причина падения.
- [ ] Известны команды GREEN и полной проверки.
- [ ] Изменение не касается БД, денег, auth, permissions, secrets или uploads.
- [ ] Изменение не создаёт dependency/provider/public API/MCP tool/AI mutation.
- [ ] Изменение не требует продуктового, визуального или security-решения.
- [ ] Откат ограничен одним атомарным коммитом.

Хотя бы один ответ «нет» означает: Luna не начинает работу; задача остаётся на
Terra/Sol/Astra или сначала декомпозируется сильной моделью.

## Обязательный handoff в Luna

Передай ей только:

1. путь к `AGENTS.md`;
2. один task packet;
3. связанные spec/plan sections;
4. точные команды baseline, RED, GREEN и full verification;
5. явное правило остановки при первом расхождении с контрактом.

Luna не должна получать расплывчатую команду «реализуй этап», «улучши UI» или
«почини всё». Один handoff заканчивается одним самостоятельно проверяемым
результатом и одним предлагаемым сообщением коммита.

## Review результата Luna

Tier A/B до commit проверяет:

- полный diff и соответствие allowed files;
- наблюдаемый RED–GREEN цикл;
- все acceptance criteria и quality gates;
- отсутствие скрытого изменения интерфейсов/зависимостей;
- security/privacy/i18n/a11y/performance по scope.

Отчёт Luna не является доказательством. Проверяющая модель повторно запускает
команды и читает их полный вывод.

## Практический порог для Memora

Для production-кода Luna становится допустима после завершения Foundation:
workspace создан, package scripts и CI определены, baseline зелёный, модульные
границы существуют в коде, а первый task packet утверждён сильной моделью.
До этого Luna безопасна только для локальной документации и иных trivial-задач,
которые проходят настоящий Luna gate.
