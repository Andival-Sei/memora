# Рабочий процесс AI-разработки

## Классификация

### Trivial

Изменение не влияет на runtime-поведение: опечатка, форматирование или точная
документационная правка. Completion criterion: целевая проверка прошла, diff
содержит только заявленное изменение.

### Bounded

Меняется существующее поведение в известных границах. Требуются task packet,
RED–GREEN, затронутый test suite и полный completion gate.

### Architectural

Меняется структура системы или контракт между частями: новый модуль/dependency,
schema, public API, auth/security, интеграция, MCP/AI capability. До кода нужны
утверждённые spec и implementation plan.

Скрытая сложность всегда повышает класс. Понижать класс после начала работы
нельзя.

## Intake

**Вход:** пользовательский запрос.

1. Прочитай `AGENTS.md`, `git status`, текущую ветку и релевантные документы.
2. Выполни `git fetch --prune`; сравни `main` с `origin/main`.
3. Отдели пользовательские изменения и сохрани их вне своего staging scope.
4. Сформулируй наблюдаемый результат и out of scope.

**Готово:** можно перечислить каждый файл/модуль, который разрешено менять, и
каждый acceptance criterion имеет бинарный результат.

**Стоп:** запрос требует нового полномочия, секретов, необратимого действия или
пересекается с пользовательскими изменениями.

## Contract

**Вход:** классифицированная задача.

1. Заполни `docs/ai/TASK_PACKET.md` в plan/task context.
2. Зафиксируй сигнатуры и owners данных до реализации.
3. Для architectural-задачи свяжи packet с утверждёнными spec и plan.
4. Пройди model gate.

**Готово:** другой исполнитель может выполнить packet без продуктового выбора.

**Стоп:** интерфейс, expected behavior или команда проверки не определены.

## RED

**Вход:** утверждённое поведение и тестовая поверхность.

1. Назови production-изменение, которое заставит тест упасть.
2. Напиши один минимальный behavioral test на один результат.
3. Запусти точную команду и прочитай output/exit code.

**Готово:** тест падает из-за отсутствующего поведения с ожидаемым assertion.
Compile/config error не является RED.

**Стоп:** baseline уже красный или тест нельзя написать без пересмотра дизайна.

## GREEN и refactor

**Вход:** доказанный RED.

1. Внеси минимальную реализацию для текущего теста.
2. Запусти целевой тест, затем затронутый suite.
3. Только при GREEN устрани дублирование/улучши имена без нового поведения.
4. Повтори проверки после refactor.

**Готово:** новый тест и затронутый suite зелёные, output чист от новых warnings.

## Verify и review

1. Выбери строки из `QUALITY_GATES.md` по типу изменения.
2. Запусти полные команды, сохрани exit codes и числа тестов.
3. Сопоставь criteria с доказательствами.
4. Выполни `git diff --check`, `git status --short` и прочитай полный `git diff`.
5. Проверь debug output, generated artifacts, secrets и незаявленные файлы.

**Готово:** выполнен `DEFINITION_OF_DONE.md`; каждый положительный claim имеет
свежую команду или наблюдаемое UI-доказательство.

## Direct-main commit и push

1. Убедись, что `main` не отстаёт от `origin/main`. При удалённых изменениях
   сначала безопасно синхронизируйся, сохранив чужой worktree.
2. Добавь в staging только allowed files или точные собственные hunks.
3. Повтори `git diff --cached --check` и прочитай `git diff --cached`.
4. Создай русский Conventional Commit по `COMMIT_CONVENTIONS.md`.
5. Выполни обычный `git push origin main`; force push запрещён.
6. Проверь `git status --short --branch`, upstream и SHA последнего коммита.

**Готово:** опубликованный commit атомарен, ветка синхронизирована, рабочее
дерево чисто либо содержит только заранее исключённые пользовательские файлы.
